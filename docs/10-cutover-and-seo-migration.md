# 10 — Cutover and SEO Migration

**Status:** Approved working specification  
**Scope:** Migration from the legacy UARoute implementation to the new route-first UARoute M1 architecture  
**Primary objective:** Launch the new UARoute without unnecessarily losing useful search equity, while removing unsupported legacy content and making the new site the authoritative route-discovery experience.

---

## 1. Purpose

This document defines the cutover strategy from the existing UARoute website to the new UARoute M1 implementation.

The migration must achieve four goals simultaneously:

1. Replace the legacy carrier-catalog experience with the route-discovery product.
2. Preserve useful existing URLs and search equity where there is a genuine equivalent.
3. Redirect obsolete URLs rather than leaving broken or misleading pages.
4. Avoid carrying unsupported legacy claims, prices, ratings, or operational data into the new site.

The migration is therefore **not** a simple visual redesign.

It is a controlled change in:

- information architecture;
- content model;
- SEO architecture;
- conversion model;
- product positioning;
- route taxonomy;
- analytics;
- technical delivery.

The central migration principle is:

> **Preserve valuable continuity, not obsolete content.**

---

## 2. Legacy-state summary

The existing UARoute implementation is a JavaScript-driven carrier catalog hosted through S3 + CloudFront.

Known legacy characteristics include:

- carrier-oriented rather than route-oriented UX;
- several carrier entries;
- Koval represented as one carrier among others;
- existing public URLs such as:
  - `/`
  - `/about`
  - `/packages`
  - `/gallery`
  - `/contacts`
- legacy assets and content that may be reusable selectively;
- metadata/branding inconsistencies;
- unsupported or insufficiently sourced route attributes;
- legacy values such as passenger price/rating claims that must not be migrated merely because they exist.

The new product intentionally narrows M1 around:

- route discovery;
- Koval-supported commercial routes;
- truthful route information;
- route-level SEO;
- inquiry intent;
- Koval handoff.

---

## 3. Migration strategy

The recommended strategy is:

```text
Inspect legacy
      ↓
Inventory URLs/assets/content
      ↓
Classify each item
      ↓
Define redirect/equivalent behavior
      ↓
Build new site
      ↓
Validate new URLs
      ↓
Deploy
      ↓
Redirect legacy URLs
      ↓
Monitor
      ↓
Iterate
```

Do not switch the domain to the new application until the redirect and canonical strategy is ready.

---

## 4. Migration principles

### 4.1 One canonical destination

Every legacy URL that remains publicly accessible should have one clear canonical destination.

Avoid:

```text
old URL → new URL → another URL
```

Use:

```text
old URL → final canonical URL
```

Avoid redirect chains.

### 4.2 Relevant equivalence only

A redirect should preserve user/search intent.

Good:

```text
legacy Koval route-like URL
→ matching UARoute route page
```

Potentially good:

```text
/about
→ /about
```

Bad:

```text
legacy route page
→ homepage
```

unless no meaningful equivalent exists.

Do not use the homepage as a universal redirect target.

### 4.3 Unsupported content must disappear

Legacy content must not survive merely because it is indexed.

Examples that must not be migrated without evidence:

- “from €100”;
- unsupported ratings such as “4.5”;
- invented travel duration;
- invented distances;
- fake schedules;
- fake stop sequences;
- unsupported availability.

Search equity is not a reason to preserve false information.

### 4.4 New architecture becomes authoritative

After cutover:

- new routes are defined by the new route data model;
- new metadata is generated by the new application;
- new sitemap is generated by the new application;
- new analytics uses the M1 event contract;
- legacy application pages are no longer the content source.

---

## 5. URL inventory

Before deployment, create a complete inventory of public legacy URLs.

At minimum inspect:

- sitemap;
- application routes;
- internal links;
- indexed/known public paths;
- redirects already configured;
- assets linked from public pages.

The inventory should produce a table like:

| Legacy URL | Type | Indexed/known | New target | Action | Reason |
|---|---|---:|---|---|---|
| `/` | home | yes | `/` | 200 | preserve root |
| `/about` | static | yes | `/about` | 200 | preserve useful page |
| `/packages` | parcel | yes | Koval package page or approved UARoute page | redirect/link | product boundary |
| `/gallery` | gallery | yes | approved replacement | redirect/retain | asset relevance |
| `/contacts` | contact | yes | `/about` or dedicated approved page | redirect/retain | avoid orphaned URL |

The exact final mapping must be determined from the actual legacy inventory before launch.

Do not invent mappings for URLs that have not been inspected.

---

## 6. URL classification

Every legacy URL should be assigned one of these actions.

### `KEEP`

The old URL remains valid in the new architecture.

Example:

```text
/about
```

if a useful equivalent page exists at the same path.

### `MIGRATE`

The old concept has a clear new canonical URL.

Example:

```text
legacy route page
→ /routes/lviv-hannover
```

### `REDIRECT`

The old URL should redirect to the most relevant new page.

### `REMOVE`

The URL has no useful user/search equivalent and should return a proper 404/410 strategy as appropriate.

### `IGNORE`

Internal, non-public, generated, or non-indexable URLs do not require public migration handling.

---

## 7. Legacy route URLs

Legacy route-like URLs require special care.

For each route-like URL:

1. determine what route/corridor the page actually represents;
2. compare it with verified M1 route data;
3. identify whether a genuine equivalent exists;
4. redirect only when the semantic intent matches;
5. otherwise remove or redirect to the nearest useful category page only when that is genuinely helpful.

Never redirect an unsupported old route to a new route merely because the city names look similar.

---

## 8. Homepage migration

The root URL remains:

```text
https://uaroute.com/
```

The homepage content changes substantially.

### Legacy positioning

The legacy product behaves primarily as a carrier catalog.

### New positioning

The new homepage presents:

- route discovery;
- route search;
- popular/approved routes;
- editorial route-atlas identity;
- Koval as the operational partner.

The root URL should remain a `200` page.

It should not redirect elsewhere.

---

## 9. `/about` migration

If the existing `/about` URL has meaningful public content, preserve the path when practical.

The new `/about` page should explain:

- what UARoute is;
- that it is a route-discovery layer;
- how Koval participates;
- what UARoute does and does not guarantee;
- the inquiry/hand-off model.

Avoid turning `/about` into generic company filler.

---

## 10. `/packages` migration

The legacy site has parcel-related functionality.

M1 is passenger-first.

Therefore `/packages` requires an explicit decision.

Preferred behavior:

- preserve the useful user-facing destination where it remains valid;
- distinguish parcel service from passenger route discovery;
- link to the Koval parcel offering where appropriate.

Do not create a passenger route page pretending that parcel handling is a passenger timetable.

If no dedicated UARoute parcel page is required for M1, a relevant Koval parcel destination may be a better target than inventing new UARoute parcel content.

The final redirect should be based on the verified current legacy URL structure.

---

## 11. `/gallery` migration

The legacy gallery may contain useful authentic Koval photography.

Possible M1 strategies:

### Retain

Keep `/gallery` if it remains useful and can be integrated into the new content model.

### Transform

Convert the assets into approved route/partner/editorial imagery while preserving a relevant public page.

### Redirect

Redirect if a standalone gallery is no longer a meaningful product destination.

Do not delete authentic assets merely because the old gallery UI is obsolete.

---

## 12. `/contacts` migration

The contact page may remain useful, but the new information architecture should avoid confusing:

- UARoute;
- Koval;
- parcel contacts;
- route inquiry desks.

A UARoute contact page should not imply that UARoute itself is the transport operator.

Possible destination:

```text
/about
```

or a dedicated contact/partner page if the new information architecture warrants it.

The exact mapping must be based on the final M1 navigation.

---

## 13. Redirect policy

Use permanent redirects only when the migration is final and semantically correct.

Preferred:

```text
301
```

or the platform-equivalent permanent redirect.

Avoid:

- JavaScript redirects;
- meta-refresh redirects;
- chained redirects;
- temporary redirects used indefinitely.

The redirect must happen at the HTTP/CDN/application routing layer.

---

## 14. Redirect map

The repository should contain an explicit redirect map.

Conceptually:

```ts
const redirects = {
  "/legacy-path": "/routes/lviv-hannover",
}
```

or an equivalent framework/infrastructure representation.

Do not hide redirect mappings inside arbitrary page components.

This provides:

- reviewability;
- testing;
- reproducibility;
- easier rollback.

---

## 15. Redirect validation

The migration test suite should verify:

- every intended legacy redirect exists;
- the response is the intended redirect status;
- `Location` points to the final URL;
- no redirect chain exists;
- destination returns `200`;
- destination canonical matches the final target;
- no redirect loop exists.

Example:

```text
GET /old-route
→ 301 Location: https://uaroute.com/routes/lviv-hannover

GET /routes/lviv-hannover
→ 200
```

---

## 16. Canonical strategy

Every indexable new page gets one absolute canonical URL.

Example:

```text
https://uaroute.com/routes/lviv-hannover
```

The canonical must not include:

```text
utm_source
utm_medium
utm_campaign
utm_content
```

It must also not depend on:

- tracking IDs;
- search parameters;
- temporary filters;
- client-side state.

---

## 17. Query parameters

The migration must distinguish tracking parameters from content URLs.

Valid examples:

```text
/routes/lviv-hannover?utm_source=...
```

may be used for acquisition.

But the canonical remains:

```text
/routes/lviv-hannover
```

Do not allow arbitrary query parameters to generate alternate indexable versions.

---

## 18. Sitemap cutover

The new sitemap replaces the legacy sitemap after the new site is validated.

It must contain:

- the homepage;
- published M1 route pages;
- approved static/editorial pages.

It must not contain:

- obsolete legacy routes;
- redirect URLs;
- unsupported route pages;
- tracking-parameter variants.

The sitemap should be generated from the new publication model.

---

## 19. Robots cutover

The production `robots.txt` should be switched to the new architecture at launch.

It should:

- allow appropriate crawling;
- identify the new sitemap;
- avoid accidentally disallowing `/routes/`.

Do not leave staging/test blocks in production.

---

## 20. Search-engine migration behavior

The desired sequence is:

```text
Google/Bing/etc.
    ↓
legacy URL discovered
    ↓
301
    ↓
new canonical URL
    ↓
new page indexed
```

For preserved URLs:

```text
existing URL
    ↓
same canonical URL
    ↓
content refreshed
```

For removed URLs without meaningful equivalents:

```text
legacy URL
    ↓
proper 404/410 handling
```

Do not try to force every historical URL into a new page.

---

## 21. SEO equity preservation

SEO equity should be preserved through:

- relevant redirects;
- stable root/static URLs where useful;
- consistent HTTPS domain;
- strong internal linking;
- XML sitemap;
- correct canonical tags;
- crawlable route pages;
- removal of contradictory metadata;
- elimination of duplicate pages.

SEO equity should not be pursued by carrying forward inaccurate legacy content.

---

## 22. Route-page introduction

The biggest new SEO asset is:

```text
/routes/<origin>-<destination>
```

These pages should be treated as first-class landing pages.

Each page must have:

- unique H1;
- unique introduction;
- truthful route/corridor description;
- operator/partner information;
- “what to confirm” section;
- FAQ where appropriate;
- inquiry CTA where commercially supported;
- internal links to related routes;
- canonical URL;
- metadata;
- BreadcrumbList structured data;
- accurate publication status.

---

## 23. Internal-link migration

Internal links must be rewritten to use the new canonical architecture.

Do not retain links to:

- obsolete route catalog screens;
- legacy carrier detail pages that no longer exist;
- temporary redirect URLs.

The goal is:

```text
new page
  ↓
new canonical page
```

not:

```text
new page
  ↓
legacy URL
  ↓
redirect
```

---

## 24. External-link considerations

Existing external sites may link to legacy UARoute pages.

Where those pages have meaningful equivalents, redirects should preserve the user journey.

Where there is no legitimate equivalent, a generic homepage redirect may be worse than a clear removal/404 because it changes user intent.

Maintain a list of important externally linked legacy URLs if this information is available.

---

## 25. Metadata migration

Legacy metadata should not be copied automatically.

For every retained/migrated page:

- rewrite the title;
- rewrite the description;
- verify H1;
- verify canonical;
- verify Open Graph data.

Do not migrate:

- unsupported prices;
- fake/legacy ratings;
- obsolete carrier comparison copy;
- claims that have no source.

---

## 26. Legacy content audit

Before cutover, classify legacy content using the data-governance model:

| Legacy item | Classification |
|---|---|
| authentic Koval photography | `keep/transform` |
| verified Koval operational claim | `verify/keep` |
| unsupported price | `delete` |
| unsupported rating | `delete` |
| route candidate with evidence | `verify/transform` |
| unsupported route | `delete/redirect` |
| generic carrier description | `rewrite` |
| obsolete carrier marketplace UX | `replace` |

This prevents old content from silently contaminating the new product.

---

## 27. Asset migration

Assets should be inventoried separately from pages.

For each useful asset record:

```text
asset path
type
owner/source
current use
new use
license/permission status
action
```

Actions:

```text
KEEP
MOVE
OPTIMIZE
RENAME
DELETE
```

Do not retain obsolete bundles simply because they are present in the old deployment.

Do not delete assets that are still referenced by the new build.

---

## 28. Branding migration

All inconsistent legacy naming should converge on:

```text
UARoute
```

The migration should remove legacy variants such as:

```text
UARoutes
UARoots
uaroots
```

where those are accidental naming variants rather than intentional historical content.

Update:

- title tags;
- manifest;
- Open Graph;
- footer;
- application metadata;
- filenames where practical;
- structured data.

---

## 29. Analytics cutover

The new application becomes the source of analytics events.

Legacy event names must not silently mix with the M1 event contract.

The launch should establish a clear boundary:

```text
legacy analytics
     ↓
migration period
     ↓
M1 analytics
```

The reporting layer should document the cutover date so that time-series comparisons are interpreted correctly.

Do not compare legacy “carrier click” events directly with new “whatsapp_click” events as if they represented the same user behavior.

---

## 30. Search Console / webmaster tools

Before launch:

- verify the canonical domain property;
- confirm sitemap submission;
- confirm HTTPS property coverage;
- ensure the new site is crawlable.

After launch:

- monitor indexing;
- inspect representative route URLs;
- monitor redirect behavior;
- monitor crawl errors;
- monitor sudden deindexing.

Search engines may take time to replace legacy URLs with new ones.

Do not react to normal short-term fluctuations by immediately restructuring the migration.

## 32. Launch sequence

Recommended sequence:

### Step 1 — Freeze legacy changes

Avoid changing the old application's routes/content during the final migration window.

### Step 2 — Build production M1

Generate the exact artifact intended for production.

### Step 3 — Validate staging

Use the production-equivalent host/configuration where possible.

### Step 4 — Run redirect tests

Verify the legacy-to-new map.

### Step 5 — Verify SEO

Check:

- HTML source;
- titles;
- canonicals;
- sitemap;
- robots;
- structured data;
- 404 behavior.

### Step 6 — Verify conversion

Test:

```text
route page
→ inquiry
→ correct Koval desk
→ WhatsApp message
```

for every configured desk.

### Step 7 — Deploy

Publish the new build to the production origin.

### Step 8 — Activate redirects

Ensure legacy routes resolve to the intended new destinations.

### Step 9 — Purge/invalidate caches

Invalidate only what is necessary.

### Step 10 — Monitor

Check:

- site availability;
- canonical URLs;
- route pages;
- redirects;
- analytics events;
- Search Console;
- CloudFront behavior.

## 35. SEO migration KPIs

Migration health should be evaluated across several dimensions.

### Technical

- % of intended redirects working;
- redirect-chain count;
- 404 rate;
- crawl-error rate;
- canonical correctness;
- sitemap validity.

### Search

- indexed M1 route pages;
- search impressions;
- organic landing sessions;
- route-query coverage.

### Product

- route views;
- booking intent;
- WhatsApp clicks;
- Koval site clicks.

Do not treat total traffic immediately after launch as the only migration KPI.

---

## 36. Traffic-drop interpretation

A temporary traffic change after a major information-architecture migration does not automatically mean failure.

Possible reasons:

- reindexing;
- canonical replacement;
- removal of low-quality legacy pages;
- search-engine reassessment;
- route pages requiring time to gain visibility.

Investigate:

```text
Which URLs lost traffic?
Why?
Did the relevant intent move to a new URL?
Is the redirect/canonical correct?
```

Do not restore low-quality legacy content simply to recover pageview volume.

---

## 37. Migration failure conditions

Treat the following as release blockers:

### Critical

- root domain unavailable;
- major route pages return 404;
- redirect loop;
- incorrect canonical domain;
- HTTP/HTTPS conflict;
- wrong Koval WhatsApp desk;
- broken inquiry flow;
- analytics sends phone numbers;
- sitemap contains invalid URLs.

### High

- large class of legacy URLs redirects to irrelevant pages;
- major internal-link breakage;
- route pages are not crawlable;
- structured data is materially wrong;
- assets are missing.

---

## 38. Rollback strategy

Rollback should be possible if a critical production problem occurs.

The rollback order is:

```text
1. Restore previous known-good production artifact
2. Restore corresponding CloudFront/origin behavior
3. Preserve redirect configuration if compatible
4. Diagnose issue
5. Rebuild and retest
6. Reattempt cutover
```

Do not delete the legacy deployment immediately after launch.

Keep the last known-good artifact available during the migration stabilization window.

---

## 39. Legacy retention window

The old application/source should remain recoverable until:

- redirects have been validated;
- analytics is stable;
- critical user journeys work;
- search engines have begun processing the new URLs;
- no major indexing/crawl issue remains unexplained.

The exact retention period is an operational decision, but it should be long enough to support a controlled rollback.

---

## 40. Migration decision matrix

Use this rule set:

| Legacy situation | Action |
|---|---|
| Same useful URL exists in M1 | Keep |
| Clear one-to-one route equivalent | 301 to route |
| Useful content but path changed | 301 to relevant new page |
| No equivalent, but user can reasonably continue elsewhere | Consider relevant redirect |
| No equivalent and no useful destination | 404/410 |
| Unsupported claim | Remove |
| Unsupported route | Do not recreate |
| Duplicate/obsolete carrier page | Redirect/remove |
| Authentic reusable asset | Keep/transform |

The key test is:

> **Would a user arriving on the destination expect to find substantially what they were looking for?**

If not, do not redirect there.

---

## 41. Special treatment of `/packages`

Because parcel service exists on the legacy site but is not the primary M1 passenger product, migration must keep a clear boundary.

Do not:

```text
parcel page
→ passenger route page
```

unless the user intent truly matches.

Prefer:

```text
parcel page
→ relevant Koval parcel information
```

when verified.

Parcel information must never be presented as a passenger timetable.

---

## 42. Special treatment of route candidates

The legacy site may contain route/city combinations that look commercially useful.

They are not automatically publishable.

Every candidate must pass:

```text
legacy candidate
    ↓
evidence review
    ↓
route model validation
    ↓
commercial or editorial classification
    ↓
publish / do not publish
```

Do not use the migration process as a shortcut to populate a large programmatic SEO footprint.

---

## 43. Content freshness after migration

Each migrated page should have:

- a clear source;
- a review owner/process;
- a last-reviewed/update value where appropriate.

Operational claims are more likely to change than stable editorial facts.

The new site must therefore avoid implying that a legacy fact remains current merely because it existed in the old application.

---

## 44. Migration and future route growth

After cutover:

- new routes are added through the new data model;
- old URLs are maintained through the redirect map;
- route IDs remain stable;
- canonical URLs remain stable;
- analytics continues to use the same event taxonomy.

Migration should be a one-time architecture change, not a recurring source of URL instability.

## 46. Final migration principle

The goal of the UARoute migration is not:

> “Keep every old URL alive.”

The goal is:

> **Preserve the value of useful existing URLs while replacing obsolete product architecture with a truthful route-discovery system.**

A successful migration leaves users and search engines with:

- fewer dead ends;
- clearer route intent;
- stronger route-level landing pages;
- cleaner canonical URLs;
- more reliable operational information;
- a better path from discovery to Koval.

**M1 cutover success = the new UARoute is the canonical route-discovery product, legacy URLs have deliberate outcomes, and no search or user value is preserved by carrying forward unsupported information.**
