# Пошук поїздки та перехід до перевізника

Дата: 2026-10-22. Статус: **проєкт специфікації для планування**. Вимоги нижче описують цільовий стан; реалізація, перевірка й публікація не виконані. Пріоритетні пасажирські міста: Львів та Івано-Франківськ.

## 1. Мета, підстава та межі

Пасажир знаходить потрібний напрямок, розуміє відому інформацію й одним очевидним кроком переходить до перевізника. Перехід на сайт перевізника доступний до введення телефону чи дати. WhatsApp залишається головною дією; сайт перевізника — помітною альтернативою без введення дати й телефону.

Підстава — запит власника та аудит опублікованого сайту 2026-10-22. Аудит виявив прихований пошук Ганновера, міські картки без підстановки міста, пізній доступ до звернення, повтори контенту та неоднозначні твердження. Повний локальний звіт збережено як `output/audits/content-audit-2026-10-22.md`; він є необов'язковим матеріалом, не залежністю перевірок документації. Цей документ зберігає всі вимоги для планування без доступу до звіту.

Доказова межа аудиту: настільний огляд 1280 × 720, інтерактивна перевірка пошуку/розвороту/картки/FAQ; мобільний порядок оцінено за кодом. Наскрізну підстановку на стороні перевізника й поведінку на телефоні тоді не перевірено. Зростання конверсії — гіпотеза. Дані про кліки з попереднього звіту не доводять отриманих звернень або бронювань.

Вища рамка: [конституція](../00-project-constitution.md), [репозиторний контракт](../Operations/Agentic/Operational/repository-contract.md), [UX](03-ux-and-information-architecture.md), [модель контенту](06-data-model-and-content-governance.md), [інтеграція](../Operations/07-koval-integration-and-conversion.md), [аналітика](../Marketing/08-analytics-and-attribution.md), [робоча угода](../Operations/Agentic/Operational/working-agreement.md).

**Уточнення власника від 2026-10-23:** WhatsApp залишається головною дією на комерційній маршрутній сторінці та в inline-зверненні. Сайт перевізника — помітна другорядна альтернатива, доступна без введення дати й телефону. За відсутності перевіреного desk основною дією стає сайт перевізника. Перенесення пріоритету на сайт скасовано; змінювати конституцію для цього не потрібно. Чинні контракти, валідація форми, referral allowlists та приватність зберігаються.

До обсягу входять головна, індекс маршрутів, комерційні маршрутні сторінки, міські огляди, форми, переходи, FAQ, пояснення ролей та перевірка спірних тверджень у статті про велосипед. Зміни застосовуються до спільних шаблонів; редакційна черга починається зі Львова → Ганновер, Львова ↔ Целле та Івано-Франківська ↔ Вольфсбурга.

Поза обсягом: нові маршрутні URL, розширення кандидатної матриці, нові перевізники, бронювання/оплата/інвентар, CRM, збереження пасажирських даних, нові канали зв'язку чи строки відповіді, розширення рекламних кампаній, зміни акаунтів, залежностей, публікація та зміни коду зовнішнього сайту. Якщо перевірка виявить дефект приймача, його виправлення оформлюється окремою залежністю.

## 2. Сценарії й маршрутизація

| ID | Початок | Цільова поведінка |
|---|---|---|
| S01 | Органічний вхід на Львів → Ганновер | На початку видно пару міст, коротку користь і реферальний перехід; для контакту не потрібно читати FAQ |
| S02 | Головна або індекс, Львів → Ганновер | Ганновер доступний у звичайному виборі; відкривається наявна комерційна сторінка |
| S03 | Львів → Вольфсбург, без окремої сторінки | Якщо пара досі допустима, показано inline-блок дій і чинну форму з цією парою |
| S04 | Обрана пара Вольфсбург / Львів | Розворот змінює порядок і країни, зберігає міста; результат визначається заново |
| S05 | Картка Шверіна на огляді Львова | Натискання вибирає Шверін у правильному полі, повертає до пошуку та фокусує наступну дію |
| S06 | Дата ще невідома або немає WhatsApp | Сайт перевізника доступний без валідації полів; обіцянок інших каналів немає |
| S07 | Населеного пункту немає | Пояснено вибір найближчого доступного міста та приватне уточнення фактичного місця без вимоги доїхати до хабу |
| S08 | Непідтримувана пара | Чесний стан відсутності інформації, повторний пошук і загальний перехід до перевізника |

**D01 — джерело варіантів.** Список доступних для вибору міст формується як об'єднання чинних обмежених кандидатних міст і кінцевих міст опублікованих комерційних маршрутів, з усуненням дублікатів за ID та обмеженням країною поля. Отже, Ганновер стає видимим без зміни `pilotGermanCityIds` і без розширення `isCandidateInquiryEligiblePair`.

**D02 — порядок вирішення.** Після вибору: (1) `findRouteByCities(..., { commercialOnly: true })`; (2) за відсутності сторінки — чинна перевірка допустимості кандидатної пари; (3) інакше — стан відсутності інформації. Вибір міста не доводить можливості перевезення. Розворот не створює симетричного дозволу: Ганновер → Львів отримує лише той результат, який дозволяють актуальні дані.

**D03 — єдиний стан.** Селектори, текстовий пошук та міські картки змінюють один стан канонічних `City` за ID. Зміна міста/напрямку скидає попередній результат, його помилки та дані його форми; заборонено надсилати попередню пару після зміни. Зміна стану сама по собі не відкриває зовнішній сайт і не створює inquiry-подію.

**D04 — міські картки.** Дія зберігає зафіксоване місто огляду та поточний напрямок. Для вже опублікованої напрямленої маршрутної картки зберігається звичайне посилання. Для вибору без сторінки — кнопка з назвою дії/міста, прокручування до пошуку й фокус; при reduced motion без анімації. Пошукові інструкції не повинні дублювати заголовок обраного міста.

**D05 — зрозумілий пошук.** Основний вибір не ховає доступні напрямки в режимі «іншої назви». Зберегти alias-пошук та його клавіатуру; явно назвати його пошуком за назвою/латинкою. Львів → Ганновер має бути видимим також у добірці маршрутів, зберігаючи пріоритет Львова/Івано-Франківська.

## 3. Ієрархія дій і сторінок

**U01 — спільний блок дій.** На комерційній маршрутній сторінці після назви й вступу показати основну дію «Уточнити поїздку в WhatsApp», що прокручує до єдиної форми й фокусує дату без валідації та conversion events, і помітне другорядне посилання «Сайт перевізника ↗», доступне без введення дати й телефону. За відсутності перевіреного desk основною дією стає сайт перевізника. Для inline-результату показати той самий зміст з обраною парою перед полями. Для огляду міста без повної пари дозволений лише чесно загальний перехід; він не видає місто огляду за вже готовий маршрут.

Під переходом коротко пояснити, що відкриється зовнішній сайт. Фото/контакти/форма згадуються лише після актуальної перевірки їх доступності. Не обіцяти на зовнішній сторінці ціну, розклад або місця.

**U02 — маршрут.** Порядок у DOM і читанні: breadcrumbs → назва/вступ → блок дій → компактні умови → єдина форма → конкретна практична інформація → FAQ → зворотний/інші напрямки → поширення. На desktop форму можна візуально поставити поруч із початковим змістом через CSS grid, не переміщуючи її після FAQ для мобільного читача. Декоративне зображення не стоїть перед початковою дією на мобільному. Окремий великий розділ, що лише повторює два міста, прибрати або згорнути в компактний контекст.

**U03 — форма.** Зберегти одну форму та спільний `InquiryProvider`, один `inquiry-anchor`, унікальні ID, чинні desk routing, обов'язкову непрошлу дату, телефон і цілу кількість пасажирів 1–8. Рання WhatsApp-дія фокусує початок форми без запуску валідації. Валідне надсилання формує повідомлення; користувач надсилає його у WhatsApp. Посилання на сайт перевізника не читає й не перевіряє телефон/дату. Не дублювати форми для різних брейкпойнтів.

**U04 — sticky.** Ранній блок дій вирішує первинний доступ. Зберегти чинний момент появи нижньої панелі після проходження форми та її спільний шлях submit/validation; не вводити другу систему конверсії. Панель прихована при фокусі у полі, враховує safe area, не перекриває контент/клавіатуру. Повторно перевірити спостереження за якорем після перестановки блоків.

**U05 — головна/індекс.** Короткий вступ → пошук → пріоритетні напрямки → коротке пояснення процесу → роль UARoute/перевізника. Прибрати повторення списків «що запитати». Пояснення процесу охоплює обидва шляхи: сайт перевізника або пряме повідомлення; проходження обох форм не є вимогою.

**U06 — міські огляди.** Зберегти початково вибране місто, прямий вибір протилежного міста, короткий nearby-контекст, окремі корисні поради виїзду/повернення. Картки виконують D04. Вибрана пара використовується тільки в пов'язаному з пошуком блоці дій, а не в незалежному серверному підвалі, де немає стану пошуку.

**U07 — запасні стани.** Стан «немає інформації» містить повторний пошук і сайт перевізника; невідому пару не передавати. Відсутній desk зберігає fallback на сайт. За помилки optional attribution посилання лишається придатним; заборонений host не отримує сформоване посилання. Editorial не отримує комерційну форму чи комерційну навігацію.

## 4. Контентний контракт

| ID | Обов'язкова вимога | Редакторська перевірка |
|---|---|---|
| C01 | Українська мова, нейтральне «перевізник» у UI, metadata, schema та повідомленнях | Немає прізвищ/брендингу, вигаданих підключень чи підтверджених рейсів |
| C02 | Вступ маршруту 1–2 речення: намір, пара міст, наступна дія | Без загальних закликів «плануйте», географічного наповнення без користі |
| C03 | Один компактний блок ключових тем: виїзд/ціна, місця, багаж, пересадки | Підтверджений факт має джерело й межі; невідоме — коротку дію для уточнення |
| C04 | Одне основне пояснення статусу звернення в контексті дії/форми | Уточнення поруч із конкретним фактом дозволене; однакові застереження в кожній секції заборонені |
| C05 | FAQ 3–5 корисних питань, якщо є стільки окремих відповідей | Не доповнювати до кількості штучно; відповідь не повторює попередній блок |
| C06 | Nearby пояснює фактичний населений пункт приватно | Немає вимоги їхати до хабу, гарантії заїзду, нових aliases/stop IDs |
| C07 | Джерело відрізняється від незалежної перевірки послуги | Для самозаявленого факту: «За інформацією перевізника…» з датою; без фальшивої сертифікації |
| C08 | Підписи посилань відповідають призначенню | «Целле ↔ Україна»; текст про міста узгоджений із вибором; «Поради» не маскує сторінку «Про UARoute» |
| C09 | Основні пояснення/альтернативні дії звичайним шрифтом від 14 px | 11 px mono залишається лише для необов'язкових декоративних метаданих |
| C10 | Ролі пояснені стисло | UARoute допомагає вибрати напрямок; перевізник погоджує і виконує поїздку; є посилання на відомості про оператора UARoute |

Пропоновані базові формулювання: «Плануєте їхати зі Львова до Ганновера? Зверніться до перевізника, щоб дізнатися про виїзд на вашу дату, вартість і місце посадки». Для форми: «Відкриється WhatsApp із готовим текстом. Перевірте його й натисніть “Надіслати”». Статус: «Дату, місця, ціну та посадку підтвердить перевізник. Звернення ще не резервує місце».

**C11 — факти, які потребують перевірки.** Перед редактурою створити перелік спірних тверджень: текст/поверхня → джерело → дата → точна сфера застосування → залишити/обмежити/прибрати. Для посадки у Стрию та комунікації водія потрібні операційні докази; географічне джерело цього не підтверджує. Для велосипеда перевірити допустимість, транспорт/пакування, електровелосипеди, універсальні «15 хвилин» і «без ризику». За відсутності доказу прибрати обіцянку або перетворити на запитання. Нові підтверджені умови багажу/оплати/пересадок — незалежне доповнення після отримання доказів; вони не блокують скорочення повторів.

Митні підсумки мають містити напрямок, істотні умови та офіційне джерело з датою перевірки; коротка картка/FAQ не може давати сильніший висновок за повний матеріал. Це вимога до майбутньої перевірки, не повторне юридичне підтвердження цифр у специфікації. Не додавати медичних/юридичних гарантій або механічних інструкцій без відповідного підтвердження.

## 5. Реалізаційні межі й компоненти

| Поверхня/модуль | Очікувана відповідальність |
|---|---|
| `src/data/queries.ts`, `discovery.ts` | Окреме формування видимих міст; чинна допустимість пар збережена; IDs і класифікації незмінні |
| `RouteSearch.tsx`, `src/app/cities/[slug]/page.tsx` | Єдиний state вибору; подія вибору картки; країни/розворот; inline-результат |
| Новий невеликий спільний блок дій, назва під час планування | Пара міст + referral link + перехід до форми; не дублює URL/desk/analytics логіку |
| `src/app/routes/[slug]/page.tsx`, `RouteSummary`, `ShareRoute` | Семантичний порядок, ранні дії, усунення повторів, перенесення поширення |
| `BookingWidget`, `CandidateInquiry`, `inquiry.tsx`, `StickyBookingBar` | Єдина форма на поверхню, чинна валідація, фокус, збережений desk routing |
| `KovalReferralLink`, `src/config/site.ts` | Єдиний чинний генератор outbound URL та коду; захисні allowlists |
| Головна, індекс, About, Footer, PartnerCard, NearbyPlaces, Faq | Узгоджені пояснення ролей, контент і підписи |
| `src/data/routes.ts`, `city-hubs.ts`, `carriers.ts`, bicycle guide | Редактура й докази в рамках scoped catalog instructions |
| `globals.css` | Лише потрібні читабельність/порядок; збереження редакційного стилю |

Server Components залишаються типовими. Client boundary потрібен лише для вибору, фокусу, форми та кліків. Міські картки не повинні перетворювати всю сторінку на Client Component; локалізувати інтерактивну межу. Не додавати залежностей або runtime server; статичний Next.js export, npm, TypeScript 6. Перед кодом читати відповідні локальні Next.js guides. Зміни каталогу виконуються за `src/data/AGENTS.md` та `edit-catalog`; UI перевіряється за `verify-pages`.

## 6. Referral, приватність і вимірювання

**R01.** Усі нові переходи використовують `KovalReferralLink`/`withUtm`. Зберегти host allowlist, `uaroute/referral/koval_poc`, approved content values, випадковий `ref_code`, complete opposite-country pair та current-visit policy. Acquisition tags/click IDs не пересилаються перевізнику. Не додавати довільні `utm_content` чи нові `ctaLocation` без узгодженого розширення enum/тестів. URL hash зараз видаляється генератором; зміна anchor/deep-link не входить у вимоги.

**R02.** Route/inline-перехід передає актуальну повну пару. Місто без пари й unknown fallback відкривають загальний сайт без неповних або вигаданих city параметрів. Зберегти baseline href для JS failure. Не передавати телефон, дату, ім'я або повідомлення в referral URL, track чи сховище UARoute.

**R03.** Зберегти first-touch acquisition окремо від поточного `targetPath`. Один прямий клік на сайт створює одну спробу `koval_site_click`; перехід до внутрішнього якоря форми не створює `booking_intent`/`whatsapp_click`. Валідний WhatsApp-submit зберігає чинні події й однаковий код у повідомленні та дозволеному telemetry context.

| Поверхня | Чинний `ctaLocation` |
|---|---|
| Ранній блок дій маршрутного hero | `hero` |
| Дія всередині маршрутної форми | `booking_widget` |
| Inline-пара | Контекст пошуку: `hero` або `route_index` |
| Міський огляд / індекс | `route_index` |
| Блок перевізника / footer / sticky | `partner_card` / `footer` / `sticky_mobile` |

Розрізняти consented route visits, переходи на сайт, WhatsApp handoffs, отримані перевізником повідомлення й підтверджені поїздки. Не додавати кліки як унікальних людей; не називати їх бронюваннями. Нові events, account settings та A/B infrastructure не потрібні. Без consent комерційний шлях працює, аналітика залишається за чинною політикою. Довгострокова оцінка — частки переходів за сторінками/каналами та незалежне підтвердження результатів перевізником; числового conversion uplift зобов'язання немає.

## 7. Критерії приймання та перевірки

| ID | Сценарій / очікуваний результат | Метод |
|---|---|---|
| AC01 | Львів → Ганновер знайдено основним вибором; відкрита саме чинна комерційна сторінка | Query tests + browser |
| AC02 | Ганновер не розширив кандидатну матрицю; непогоджена/зворотна пара не стала eligible автоматично | Незалежні expected sets + негативні тести |
| AC03 | Картка Шверіна вибирає його в потрібне поле, зберігає Львів/напрямок, ставить фокус | Browser click + keyboard |
| AC04 | Львів / Вольфсбург розвертаються без втрати міст; країни й результат правильні; inline eligibility чинна | Browser в обох напрямках |
| AC05 | Зміна міста після результату не залишає стару форму/пару для надсилання | State regression + browser |
| AC06 | На 375 × 812 і 1440 × 900 основна WhatsApp-дія повністю в межах першого viewport (за відсутності перевіреного desk — дія переходу на сайт перевізника) після звичайного завантаження без перекривного consent dialog | Screenshot + DOM bounds; відкритий dialog перевіряється окремо |
| AC07 | На 360 px, з 200% zoom/довгим заголовком немає горизонтального scroll; дія до FAQ/інших маршрутів і не перекрита | Browser, readable screenshots |
| AC08 | На сторінці одна форма/anchor/набір ID; рання WhatsApp-дія фокусує форму без telemetry submit | DOM + keyboard + interception |
| AC09 | Відсутня/минула дата, невалідний телефон, count поза 1–8 не відкривають WhatsApp; referral працює з порожніми полями | Фокусовані validation tests + browser |
| AC10 | Передано правильну повну пару, чинний desk, referral tuple/code; немає персональних даних чи acquisition click IDs у referral/analytics | Перехоплення запитів і handoffs |
| AC11 | Без JS baseline referral link придатний; без consent обидва контактні шляхи доступні | Browser contexts |
| AC12 | На приймачі в контрольованій fixture/export підставлено дозволену пару та збережено код; реальний запит не надіслано | Сумісний snapshot приймача; без нього позначити UNVERIFIED dependency |
| AC13 | Немає нових editorial маршрутів у discovery/sitemap; canonical, H1, metadata/schema узгоджені з видимим українським контентом | Catalog/SEO tests + export inspection |
| AC14 | Важливі targets від 44 px; фокус видимий, порядок логічний, FAQ доступний, reduced motion враховано; текстовий contrast не менше 4.5:1 | Browser + вимірювання контрасту |
| AC15 | Кожен змістовий блок має окреме питання; FAQ не повторює його; усі сильні факти мають рішення в evidence register | Редакторська перевірка C01–C11 |
| AC16 | Чинні Celle/Стрий сценарії перевірено за актуальним каталогом; не змінено пари за старим прикладом із skill/історії | Початкова фіксація матриці + regression |

AC06 є цільовою вимогою майбутньої реалізації, а не результатом аудиту. На менших/масштабованих viewport перевага читабельності: не зменшувати шрифт заради формального першого екрана. Consent dialog не прибирають заради цієї умови.

Усі зовнішні collectors і handoffs перехоплюються до QA-вводу. Використовувати disposable fixtures/canaries, не надсилати диспетчеру й не створювати службові conversion events у робочій аналітиці. Знімки екрана доповнюють кліки/клавіатуру. Відсутню fixture приймача не називати успішною перевіркою.

Під час реалізації: focused tests для вибору/eligibility/referral/validation та зміненого контенту; потім один `npm run check` на стабільному кандидатові Node 22 згідно з `.nvmrc`; browser acceptance на тому самому export. Node 24 — лише за runtime/release scope. Документування цієї специфікації: `npm run docs:index`, `npm run docs:check`, відповідні OKF tests. Публікація має окремий release scope за [CUTOVER](../../CUTOVER.md).

Якісна перевірка після робочого кандидата: 5–8 нових людей виконують S01–S07 без підказок. Записати успіх завдання, перше помилкове натискання й пояснення «хто відповідає / що відкриється / чи заброньоване місце». Умова: немає невирішеної блокувальної проблеми пошуку/контакту або хибного розуміння бронювання; проблеми виправлено і повторно перевірено. Це мала якісна вибірка, без статистичних claims про conversion uplift.

Власники відповідальностей для плану: product owner — ієрархія дій і публікаційний scope; редактор — C01–C11 та відсутність повторів; розробник — D/U/R і докази AC; перевізник — джерела операційних фактів; verifier — review за матрицею. Це розподіл ролей для майбутньої роботи, не призначення агентів або строків.

Під час оцінювання зафіксувати baseline source/export, актуальний каталог, незавершені зміни користувача, snapshot приймача та перелік необхідних змін контрактів. Вибір конкретної назви нового компонента, diff розбиття й оцінка строків належать наступному плану. Не робити реліз W2 з невирішеною суперечністю контрактів або називати W5 пройденим без потрібних доказів.
