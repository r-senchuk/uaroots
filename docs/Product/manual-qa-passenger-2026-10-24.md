# Manual QA: сайт очима пасажира

Дата пакета:24 жовтня2026. **Це план тестування, не звіт PASS. Усі кейси починаються з NOT RUN.** Production baseline — застосунок `dac7e98735eabfdda8abb7df37fb6e59428b22be`; наступний documentation commit не доводить нового application deployment. Перед прогоном developer записує фактичний deployed SHA/artifact і середовище; якщо версія інша — expected results звірити з чинним каталогом.

Джерела: [пасажирська специфікація/AC01–AC16](passenger-discovery-conversion-spec-2026-10-22.md), [актуальна стратегія](development-strategy-2026-10-24.md), [release receipt](../../ops/evidence/production-release-2026-10-24.json), [поточний register](../../ops/agent-state.json). Автоматичні перевірки вже є; тут потрібно пройти дії руками й оцінити зрозумілість. Старі automated PASS не заповнюють результати цього пакета.

## 1. Перед стартом: два різні режими

**A — огляд production без звернень.** Дозволено відкрити сторінки, відмовитися від аналітики, шукати міста, міняти напрямок, читати FAQ, користуватися внутрішніми links, фокусувати порожні поля та копіювати public route URL. Не заповнювати date/phone тестовими даними, не submit inquiry, не активувати зовнішні contact/site links. Їх href можна скопіювати й оглянути локально. Не обирати consent «Дозволити аналітику» у live QA: це забруднює production вимірювання. Не називати A повним end-to-end тестом.

**B — повний ручний QA у підготовленому ізольованому browser-контексті.** Developer надає exact QA export/URL з тим самим build/analytics mode, локальний capture і перевірене перехоплення ВСІХ collectors, зовнішніх site/WhatsApp handoffs та popup/native-app викликів ДО вводу. Аналітику можна приймати тільки тут із mocked/blocked provider. Одного «я не натисну Надіслати у WhatsApp», incognito або ad blocker недостатньо. Не використовувати DevTools Offline як заміну: воно ламає сам сайт. Налаштування не поширюються на особистий browser/account користувача.

Developer демонструє перед стартом: synthetic test request і window.open потрапляють тільки в local capture; невідомі зовнішні origins заборонені; service workers blocked; жодної live collector delivery. QA отримує індикатор готовності, шлях/місце capture й інструкцію очищення між кейсами. Якщо цього немає — B=BLOCKED, A можна продовжувати. Підготовка інтерактивного B-контексту — окрема developer задача; наявний headless harness не видавати за вже підготовлене manual workspace.

**F — спеціальна fixture.** Окремий hydrated no-desk або injected-error стан. Ніколи не видаляти production desk/маршрут і не публікувати QA page заради тесту. У звіті fixture позначається окремим artifact; її PASS не означає PASS production для недосяжного стану.

Не надсилати повідомлень перевізнику, не робити справжніх заявок, не публікувати share у чатах. Не вводити справжні телефони, дати поїздок, імена чи click IDs. У баг-репортах редагувати PII/canaries/повідомлення/коди; повний HAR зі сторонніми cookies/токенами не прикріплювати.

### Тестові дані лише для B

- ДатаD0 — локальне «сьогодні» у browser timezone; D+1 — завтра, D−1 — вчора. Перед кожним днем прогону перерахувати, не прив’язувати до24 жовтня.
- Форматно валідний синтетичний телефон: `+380000000000`; не вважати його реальним номером і не відкривати live WhatsApp. Невалідні: порожнє, `12`, `abc`, `+3800000000000000`.
- Passengers: default1; valid1–8; developer-injected negatives0/9/1.5/NaN. Відсутні options не інжектувати руками на live.
- Жодних справжніх gclid/gbraid/wbraid; acquisition fixtures тільки в B. Дані message оглядаються локально, не публікуються в report.

## 2. Як проводити прогін

1. Записати QA name/date/build/origin/OS/browser/version/device/viewport/zoom/consent/network mode. Для B — capture readiness і sender/receiver artifact identities.
2. Спочатку пройти smoke: QA01–QA04,QA07–QA11,QA18,QA31. P0=must-have для основного шляху; це пріоритет тесту, а не автоматична severity будь-якого знайденого дефекту.
3. Виконати решту кейсів за матрицею. Межі mode важливіші за бажання «усе проклікати» на live. B/F без готовності позначати BLOCKED.
4. Для кейсу записати actual result і UX observation окремо. PASS потребує виконаних steps/expected, а не відсутності Console errors.
5. Після bug fix повторити точні repro steps на новому build, потім сусідній route/inline/reverse кейс. Не змінювати старий FAIL заднім числом: додати retest row.

Статуси: **NOT RUN / PASS / FAIL / BLOCKED / N/A**. N/A має причину, наприклад mobile sticky на desktop. Загальне «пройдено на Chrome» без build/розміру не є результатом.

### Browser/device matrix

| Середовище | Мінімальний обсяг |
|---|---|
| Desktop Chrome,1440×900,100% | Увесь A+B core, клавіатура, contact/header/footer/unknown/referral |
| Реальний iPhone Safari, portrait | Search/autocomplete/tap/date picker/keyboard/sticky/consent/share; записати фактичну CSS-ширину |
| Реальний Android Chrome, portrait | Те саме; нативні controls/клавіатура відрізняються від iOS |
| Responsive360×812 і375×812 | First screen на375; long heading/overflow/FAQ/sticky на обох; емуляція не замінює real phone |
| Desktop Firefox або Safari | Основний пошук+reverse+Enter+links+layout; порівняти з Chrome |
| Native browser zoom200%, reduced motion | QA32–QA34; фактичний mode і layout width, не лише deviceScaleFactor |
| Screen reader NVDA/VoiceOver | QA33; якщо недоступний, явно NOT RUN |

Чиста нова сесія потрібна для consent/acquisition. Для решти відмовитися від аналітики один раз і не починати кожен кейс із нового dialog. Перший екран оцінюється після normal fonts/layout settle, на самому верху, без перекривного consent dialog; dialog теж перевіряється окремо. Не видаляти його CSS/DOM і не зменшувати шрифт заради PASS. Screenshot фіксує стан, а не замінює клік/keyboard перевірку.

## 3. Детальні test cases і reproduction steps

### QA01. Перший вхід і відмова від аналітики

**Пріоритет:** P1 · **Режим:** A · **Покриття:** AC11, AC14

**Старт / передумови:** Нове приватне вікно → https://uaroute.com/. Consent і device — за matrix, capture очищений перед новим B-сценарієм.

**Кроки:**

1. Не натискаючи нічого, оглянути перший екран і прочитати consent dialog.
2. Натиснути «Без аналітики». Повернути сторінку на самий початок.
3. Перейти в «Маршрути», повернутися назад і перезавантажити сторінку.

**Очікувано:** Діалог читається й має доступний вибір відмови. Після відмови пошук і контент працюють; повторного примусу погодитися немає. Для enabled production кнопка називається «Без аналітики»; інша назва в disabled QA build не є дефектом сама собою.

**Що спостерігати в UX:** Чи зрозуміло, що відмова не забирає можливість звернутися? Чи легко знайти обидва варіанти?

### QA02. Пошук Львів → Ганновер основним вибором

**Пріоритет:** P0 · **Режим:** A · **Покриття:** AC01, AC02

**Старт / передумови:** https://uaroute.com/. Consent і device — за matrix, capture очищений перед новим B-сценарієм.

**Кроки:**

1. Обрати «До Німеччини», українське місто Львів і німецьке місто Ганновер.
2. Натиснути «Знайти маршрут».
3. Оглянути адресу, заголовок, дії та форму.

**Очікувано:** Відкривається /routes/lviv-hannover/ з правильним напрямком. Ганновер доступний у звичайному списку без відкривання режиму латинки; немає другого однойменного пункту.

**Що спостерігати в UX:** Чи можна знайти Ганновер із першої спроби? Чи зрозуміло, що саме відкриється?

### QA03. Непогоджений зворотний Ганновер

**Пріоритет:** P0 · **Режим:** A · **Покриття:** AC02, AC04

**Старт / передумови:** https://uaroute.com/routes/. Consent і device — за matrix, capture очищений перед новим B-сценарієм.

**Кроки:**

1. Обрати Львів і Ганновер.
2. До натискання пошуку перемкнути «До України». Перевірити міста й порядок полів.
3. Натиснути «Знайти маршрут». Потім перевірити Івано-Франківськ → Ганновер.

**Очікувано:** Розворот зберігає міста, змінює порядок на Ганновер → Львів. Для обох непідтриманих пар немає published route або inline inquiry; є чесний стан відсутності інформації й загальний сайт перевізника. Не робити висновок, що поїздка неможлива взагалі.

**Що спостерігати в UX:** Чи зрозуміло, як діяти далі й змінити пошук?

### QA04. Inline Львів ↔ Вольфсбург

**Пріоритет:** P0 · **Режим:** A; поля не заповнювати · **Покриття:** AC04, AC05, AC08

**Старт / передумови:** https://uaroute.com/routes/. Consent і device — за matrix, capture очищений перед новим B-сценарієм.

**Кроки:**

1. Обрати Львів → Вольфсбург і знайти маршрут.
2. Оглянути inline пару, WhatsApp/сайт і поля, не вводячи тестових даних.
3. Перемкнути «До України» й повторити пошук.

**Очікувано:** Показано inline-блок з обраною парою на поточній сторінці, без вигаданої route URL. Після розвороту попередній блок зникає до нового пошуку; новий результат Вольфсбург → Львів. Обидва напрямки допустимі.

**Що спостерігати в UX:** Чи зрозуміло, що можна звернутися прямо тут, не шукаючи іншої сторінки?

### QA05. Пошук латинкою й клавіатурою

**Пріоритет:** P1 · **Режим:** A · **Покриття:** AC01, AC14

**Старт / передумови:** https://uaroute.com/. Consent і device — за matrix, capture очищений перед новим B-сценарієм.

**Кроки:**

1. Відкрити «Пошук за назвою або латинкою». У «Звідки» набрати Lviv.
2. Вибрати підказку стрілками та Enter; у «Куди» набрати Hannover і вибрати її.
3. Перевірити Escape, Tab, повернення в поле та вибір підказки мишею/тапом. Знайти маршрут.

**Очікувано:** Обрано канонічні міста Львів і Ганновер; відкривається правильна сторінка. Enter у відкритому списку вибирає підказку, не створює contact handoff. Escape закриває список. На touch підказку теж можна вибрати.

**Що спостерігати в UX:** Чи відрізняється обране місто від просто введеного тексту? Чи підказки не губляться за екраном?

### QA06. Неповний або невідомий пошук

**Пріоритет:** P1 · **Режим:** A · **Покриття:** AC05, AC14

**Старт / передумови:** https://uaroute.com/. Consent і device — за matrix, capture очищений перед новим B-сценарієм.

**Кроки:**

1. Очистити одне місто й натиснути «Знайти маршрут».
2. У текстовому режимі набрати вигадану назву «ТестовеМістоXYZ», не вибирати підказку й повторити.
3. Виправити на Lviv/Celle, вибравши підказки, й повторити.

**Очікувано:** Є зрозуміле пояснення/вимога обрати міста; довільний текст не стає новим містом чи маршрутом. Після виправлення працює чинний /routes/lviv-celle/. Старий результат не лишається активним.

**Що спостерігати в UX:** Чи пояснення допомагає виправити дію, а не просто каже «помилка»?

### QA07. Міська картка Львів → Шверін

**Пріоритет:** P0 · **Режим:** A · **Покриття:** AC03, AC04

**Старт / передумови:** https://uaroute.com/cities/lviv/. Consent і device — за matrix, capture очищений перед новим B-сценарієм.

**Кроки:**

1. Знайти картку Шверіна та натиснути дію вибору міста.

**Очікувано:** Зберігається місто огляду Львів; у правильному полі з’являється Шверін. Сторінка повертається до пошуку, фокус на наступній дії. Результати Львів → Шверін / Шверін → Львів мають правильний порядок.

**Що спостерігати в UX:** Чи здається картка дієвою? Чи видно, що змінилось після натискання?

**Що спостерігати в UX:** Чи зрозуміло, які картки відкривають поради, а які лише вибирають місто?

### QA12. Скидання inline після зміни пари

**Пріоритет:** P0 · **Режим:** B · **Покриття:** AC05

**Старт / передумови:** https://uaroute.com/routes/. Consent і device — за matrix, capture очищений перед новим B-сценарієм.

**Кроки:**

1. Знайти Львів → Вольфсбург, ввести тестові дату/телефон, вибрати8; отримати помилку невалідним телефоном.
2. Змінити німецьке місто на Шверін, не виконуючи новий пошук.
3. Перевірити зникнення старої форми, потім знайти нову пару; повторити зі зміною напрямку.

### UX scorecard після кожної задачі

Оцінити1–5: зрозумілість мети сторінки, пошук потрібного напрямку, очевидність наступної дії, читабельність/тапи, розуміння ролей і статусу звернення.1=не зміг/не зрозумів,3=виконав із сумнівами чи перечитуванням,5=самостійно й правильно пояснив.
