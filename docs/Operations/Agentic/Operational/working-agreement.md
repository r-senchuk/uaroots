# Working agreement

**Effective 2026-10-10.** Owner-requested efficiency update; explicit task requirements take precedence. This agreement replaces blanket full-release treatment of every small follow-up. Product constraints remain in [repository contract](repository-contract.md) and [constitution](../../../00-project-constitution.md).

## Choose the execution size

| Work | Default execution | Acceptance |
| --- | --- | --- |
| Documentation/instructions | Coordinator edits directly; relevant references only | `docs:index`, `docs:check`, instruction structure/link checks; tooling tests if changed |
| One bounded content correction | One implementer; source review only for changed factual claims | Relevant content/SEO/validator tests together, one stable `npm run check`, changed-page browser flow |
| Behavior/catalog/SEO change | Plan dependencies and explicit ownership; separate candidate copy when delegated/isolation required | Relevant negative cases, stable full check; affected UI/privacy/routing gates |
| Runtime/security/release | Explicit acceptance matrix and immutable candidate/artifact | Required Node matrix, analytics modes, performance/privacy/browser/routing/recovery evidence |

Do not retroactively relax an explicit acceptance contract. A small copy change does not automatically require Node24, two analytics builds, repeated full-site privacy sweeps or new performance infrastructure. When these are required by the active task, batch them once after content/test acceptance. Publication remains independently authorized; authorization already supplied persists within scope.

## Context and preparation

For cross-session resumption, read the [checked state-register contract](state-register.md) and run `npm run state:check`. The register is dated evidence, not live state or authorization. Recheck only the resource needed for the next dependent action; update the register after a verified change or meaningful handoff. Do not repeat the whole historical audit.

1. Record path, HEAD/branch and dirty file scope. Preserve contributors' work. Read the relevant scoped instructions and current source before editing; do not load a vault tree or historic transcript.
2. State the intended behavior in one concrete example. For nearby destinations: Ukraine → Lachendorf uses Celle in selection and the private request names Lachendorf. The same mechanism applies in reverse. A selected hub does not require boarding in that hub.
3. Find the implementation and all dependent expectations in one search: source content, validator tests, export fixture, inspector, sitemap dates and browser scenarios. Assign the complete bounded change, including fixtures, before dispatch.
4. Establish runtime/tool availability before a worker starts. Prefer an already available CI-matching runtime; do not upgrade dependencies or user-global tools for convenience. Prepare ignored evidence needed by strict local checks with provenance before checking an isolated copy.
5. A Git-base worktree does not inherit dirty files. For Vibe, use supported reviewed preparation, hash source/base/overlay and verify required bytes before inference. Never modify its active worktree externally or ask it to reconstruct missing inputs.

## Delegation and tool use

Use one agent for small dependent edits. Delegate only when the user/scoped instruction asks, or the authorized task clearly benefits and delegation is permitted by the active harness. Direct coordinator execution is the default for docs/typos. No separate user-owned chats for subtasks.

A worker contract supplies outcome, exact owned paths, baseline/candidate identity, permitted tools, exclusions, concrete acceptance criteria and budget. Include: “You share this codebase with other contributors. Preserve their changes. Edit only your assigned files and adapt to existing work. Do not revert unrelated changes.”

Confirm a permitted read and edit tool is actually callable before inference; avoid discovering this after dispatch. Read-only/write-only workers do not run tests; coordinator verifies. For authorized Vibe fallback preserve the exact requested provider/model/reasoning; never silently substitute. Restrict Vibe to its supported read/search/write/edit tools, never shell/network/test/commit/merge/source-patch tools.

Use current Vibe Supervisor/ACP skills only for an actual Vibe task. Inspect schemas/owning connection first. Installed CLI, connected server and saved-run creator identities are separate; unknown remains unknown. One preflight per unchanged connection/configuration is enough. On a failed prerequisite, preserve the first diagnostic and use the authorized fallback; provider repair is a separate task. No incidental recovery/soak campaign, guard bypass, credential copying or configuration/allowlist expansion.

For an explicitly bounded Vibe increment, retain the approved cumulative ceiling (Celle protocol: at most 40 turns / 900 seconds / three focused correction rounds), reserve export/cleanup time, use cursor-based waits normally 30 seconds, require `end_turn` and a real final answer, keep usable ACP open during independent verification, fetch a fresh export after every correction, and verify supported safe cleanup. Never infer quota/provider failure from silence, replay uncertain work, enlarge limits or force-delete resources. These are maximums for that protocol, not required spending or universal provider defaults.

Do not launch VS Code or another IDE unless an upcoming action requires its editor, debugger or extension. State the purpose first and use the surface. Prefer purpose-built tools/CLI for file edits, checks and artifacts. Do not open a second control surface merely to “prepare” a session.

## Verification and correction loop

- Run focused dependency tests first. Batch all related failures into one correction, rather than repeatedly running the complete pipeline to discover stale fixtures one at a time.
- Preserve independent expected sets and negative tests. Fixtures may reflect current markup without importing production output. React comment/inline-element whitespace must not produce false text failures; semantic normalization must keep missing-content checks.
- Freeze a stable candidate, then perform the required broad check once. Repeat affected checks after edits; repeat the full pipeline only when a new failure, changed dependency or release contract justifies it.
- Use bounded waits of30–60s with progress updates when work is ongoing. Do not poll an unchanged worker every 10 seconds while having no independent work. Prefer completion events/cursors and useful concurrent work.
- Keep build configurations sequential if they share `.next/`/`out/`. Parallelize independent reads/checks only. Bind each result to source candidate and build configuration; “same source” is not “same artifact”.
- Click changed behavior, including keyboard focus, search/reversal and inquiry boundary as relevant. Screenshots alone are insufficient. Capture the changed section at readable scale, not only a 9,631px page reduced to 80px wide.
- Intercept collectors/operator handoffs and use synthetic canaries. Do not send QA inquiries. Lab comparisons must use comparable tools/environment/configuration; small differences within sample spread are not proven regressions. Field CWV remains unknown without field evidence.

## Evidence and completion

For small edits keep one review note: scope, changed files, actual provider/tool identity, commands/runtime/status, candidate fingerprint, source dates and publication state. Add traces/full CE matrices/recovery bundles only for explicit release/risk scope. Hash candidates after meaningful edits, not every idle status poll. Record first relevant failures and final accepted evidence; no transcripts/reasoning, credentials or invented token/cost numbers.

Memory records distinguish observations from inferences and proposed improvements from implemented controls. Promote an accepted recurring rule here or to a scoped skill; avoid appending each incident to root AGENTS.md. Existing evidence is not re-certified by indexing/Markdown checks.

Before finishing, verify the exact final bytes and affected checks, account for scratch/resources, and report what is local, committed or deployed separately. Commit/push/release only within actual user authorization; never treat an old deployment as publication of a new correction. GitHub Actions/OIDC and [CUTOVER](../../../../CUTOVER.md) govern deployment/recovery.

After an external write, verify saved state before claiming completion; after an uncertain timeout/interruption, read state before retrying the mutation. Save a sanitized readback or label the record as a session transcription. Do not assume a browser editor or save spinner proves persistence. Use narrow tool discovery and confirm resource scope/read-write capability once per unchanged connection; missing capability does not authorize broader credentials, subscriptions or incidental global configuration changes.

## Setup evaluation

On the next three small edits record wall time, number of full checks/builds, correction rounds, tool launches and actual tokens/cost only if reported by the runtime. Target: all dependencies in the initial ownership packet, at most one stable full check, no unused IDE, no repeated failed preflight. These are process goals, not measured speedup claims. Revisit this agreement after those samples or a model/tool major version change.
